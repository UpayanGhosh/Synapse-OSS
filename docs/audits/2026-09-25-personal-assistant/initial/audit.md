# Synapse: current condition

Synapse has the core pieces of the assistant you described. Messages are captured before the model replies. It keeps recent chat history, stores structured personal facts, has a database and a knowledge graph, searches older conversation chunks, tracks coarse emotional signals, and builds a prompt that combines memory with style and personality rules. WhatsApp, Telegram, Discord, and direct chat use a shared conversation pipeline. This is a substantial foundation.

The experience you want is still incomplete. A reply can work while the assistant feels as if it does not really know you, because several steps between hearing a detail and recalling it naturally are conditional, delayed, or insufficiently precise. This audit is based on current source paths and synthetic checks, not a measurement of your personal chats. I would not assign a completion percentage from this evidence.

The five main reasons are:

1. **A conversation can be saved without becoming searchable soon.** Each incoming turn is written to a transcript. The immediate structured memory pass catches a defined set of patterns such as preferences, relationships, and routines. Broader conversation details enter vector memory and the graph after `/new` or a periodic flush. The active chat history helps for recent turns, but a meaningful moment can remain unavailable to long-term search in the meantime.
2. **Memory retrieval needs a person boundary.** The session and structured-fact paths use session identifiers, but the shared vector search and graph lookup do not filter by user. The queries for always-included profile documents and recent archived conversations also lack a user filter. On a one-person installation this can add unrelated context. If multiple people use the same installation, it can reveal one person's memories to another.
3. **The reply prompt does not consistently receive relevant memories.** Fast casual turns allocate no dynamic memory snippets, even though a search already ran. More capable prompt tiers generally take the nearest memories without a minimum relevance threshold. Those two choices can produce opposite bad experiences: no visible recall in everyday chat, or an unrelated old detail brought up as if it matters now. Stable profile facts and recent chat history still exist, so this is a gap in episodic recall rather than total memory loss.
4. **The stored time and emotion do not identify a specific moment well enough.** Normal transcript turns have no event timestamp. Archived chunks get the ingestion date, and emotional tags are calculated for a chunk of user messages. The system can infer a broad mood, but it has weak evidence for a natural, accurate reference such as “you were stressed when we spoke Tuesday night.”
5. **Memory-save success does not prove later recall.** If embedding generation fails, the code substitutes a zero vector. If indexing into the vector store fails, a database row can still be reported as stored. Search reads the vector store. These are conditional failure paths; this audit does not establish that they happened on your machine.

Personality has useful rules already: it chooses a style, a social stance, and shorter replies for very short messages. It leaves longer user messages without the same short-reply constraint, so the friend-like conversational length is guided rather than guaranteed. The separate “parallel memory agent” in your concept is not the current default execution pattern: the chat path retrieves memory before planning the response. That is mainly an architecture and latency choice; accurate recall matters more to the user experience.

**Recommended sequence:** First make every memory and graph query respect the current person, and prove isolation with two users who mention the same names and topics. Next make indexing status honest and retryable, while storing a timestamp for each turn. Then shorten the delay before a meaningful moment becomes searchable, add a relevance gate, and reserve a small episodic-memory budget for normal casual messages. Finally tune the reply-length policy and run longitudinal acceptance conversations that include corrections, emotional context, `/new`, restart, and cross-channel follow-ups. Repair the existing memory loop and pass those scenarios before adding new features.

Detailed source evidence: [architecture.md](./architecture.md). The [verification record](./evidence.md) reports three passing deterministic evaluations: two distinct configured styles, three distinct compiled profiles, and a scripted memory canary that persisted 20 documents, 20 affect rows, and 11 facts. Two focused probes reproduced the zero-vector embedding fallback and the casual prompt dropping episodic and graph context while retaining permanent profile and affect hints. These are useful wiring checks. They did not generate real replies, measure retrieval quality, exercise channels, or test cross-user isolation. Full memory-engine integration was unavailable because this environment lacks `pyarrow`. Whether Synapse feels natural still needs observed multi-turn conversations assessed against expected facts and tone.
