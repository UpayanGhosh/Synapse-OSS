# Current → proposed: gaps, reuse, and build order

The [current map](./current-architecture.md) describes wired source paths; the [target architecture](./target-architecture.md) is a proposal. The [initial audit](./initial/audit.md) concentrates on memory and personality. The immediate engineering goal is a **general durable task loop**, not a hardcoded reminder, travel, or shopping assistant.

| Capability | Current implementation | Reuse and necessary change |
| --- | --- | --- |
| Channel input | WhatsApp/Telegram/Discord/Slack adapters, webhook routes, FloodGate, in-memory queue | Keep adapters and message normalization; commit a deduplicated inbound envelope before acknowledging it. Work from a durable queue/lease, not process memory alone. |
| Identity/session | Per-channel-peer session keys and optional configured links; phone/keyword persona routing defaults to creator | Keep session-key construction, then add an authenticated person registry and explicit cross-channel linking. Separate persona/relationship style from identity. |
| Personalization | SBS, profile prompt, immediate structured facts, session ingest, SQLite/LanceDB/KG | Preserve these stores and prompt compiler. Enforce person/grant scopes on every search/traversal; add event timestamps, provenance, correction, relevance threshold, indexing status/retry, and casual episodic budget. |
| Model behavior | LLM router, tool loop, skill router, style and stance policy | Keep routing/loop. Add provider capability negotiation and a deterministic goal coordinator; do not treat model output as proof of an action. Evaluate real short-conversation quality. |
| Tools/integrations | Static tool registry, optional MCP host, Calendar/Gmail/Slack servers, Google OAuth hub, web query | Keep adapters and registry surfaces. Unify them behind typed capability metadata, per-person account grants, health/freshness/rate limits, result provenance, and precise action receipts. Add Maps/weather/merchant capabilities only when real supported integrations exist. |
| Background work | Persisted cron jobs, optional proactive polling, optional `GentleWorker`; some direct sends | Keep cron parsing and policy as migration input. Add goal/event ledger, versioned task state, leases/checkpoints, event reconciliation, cancellation, and one outbox path for *all* send origins. |
| Delivery | Channel `send`, WhatsApp worker reply SQLite retry queue; no uniform status receipts | Reuse transport adapters/retry mechanics. Route reply/reminder/proactive/action outcome through a common outbox; distinguish accepted/delivered/read and reconcile uncertain sends. |
| Control plane | CLI onboarding, workspace seed files, dashboard/config, integration connect flows | Keep as the setup surface; expose identity links, grants, task status/cancel, connection health, and delivery evidence in plain language. |

## Highest-priority repair sequence

1. **Make identity and privacy real.** Assign every turn, memory, tool credential, task, and outbox item to an authenticated person. Test two people discussing overlapping names/topics and prove no private leakage. Separate consented shared preferences from private chat; implement use-versus-quote grants and revocation filters. This addresses both personalization confusion and the most consequential multi-user risk.
2. **Make input and output durable.** Insert inbox/dedupe records before webhook acknowledgement. Put all outbound sends through a transactional outbox with attempts and receipts, including cron and proactive. The targeted cron probe in [architecture evidence](./architecture-evidence.md) shows why: a failed one-shot WhatsApp send was marked successful and had no next run or worker retry. Use at-least-once semantics with provider-aware dedupe, and recheck cancellation/grants at dispatch.
3. **Make existing memory truthful and timely.** Persist per-turn event/observed times, make vector indexing failure explicit and retryable, rebuild derived indexes from source records, and apply relevance/abstention before prompt injection. Consolidate meaningful moments before a 50-message/6-hour gap when possible. Test corrections and emotional recall longitudinally, not just synthetic prompt differentiation.
4. **Introduce the generic goal/workflow ledger.** Persist tasks with owner, version, due time, timezone, checkpoints, attempts, result state, and cancellation. Migrate JSON cron jobs carefully to avoid duplicate/lost sends; preserve old behavior during cutover. A deterministic coordinator turns supported requests into executable steps and exposes progress. The worker survives restart and chat disconnect.
5. **Unify capabilities and evidence.** Adapt the existing tool registry, MCP client, OAuth hub, and router into typed read/compute/write/schedule/monitor capabilities. Per-person token references and narrow scopes are required before unattended tool use. Result source, freshness, units, timezone, and receipts become explicit. Add Calendar event sync/reconciliation and needed Maps/weather sources; treat merchant actions as unavailable until verified integration exists.
6. **Prove user journeys end to end.** Tuesday scheduling through Saturday delivery/retry/cancel; two people with private and consented shared tastes; 5 p.m. Calendar departure that changes with traffic/weather or falls back honestly; uncertain side-effect execution that reconciles before retry. Run connected-channel canaries only after synthetic fault injection and privacy tests pass. Measure actual outcomes and conversational feel independently.

## Tradeoffs and rollout risk

The proposed design adds schema, worker, and migration work. Inbox/outbox and task leases cost more operational effort than a process-local queue, but directly close acknowledged-message loss and unverified background-send paths. Policy-scoped hybrid retrieval and fresh external tools add latency; parallelize independent reads within a bounded budget, then abstain or send the time-critical plain reminder if enrichment misses its deadline. More model options reduce provider lock-in but cannot make all models equally capable at planning or natural dialogue; negotiate supported schemas and test quality by tier. SQLite is appropriate for one-user or small-household deployments if transactions and locking are designed carefully; growth or always-on hosted multi-tenancy may later justify a different source-of-truth store. Avoid that migration until actual load and deployment requirements demand it.

One physical database simplifies transactions but is safe for multiple people only if owner and grants are mandatory on every query and graph edge. Revocation cannot wait for vector/KG rebuild: source-of-truth tombstones must filter stale projection results immediately. External actions cannot be promised exactly-once; task records, idempotency keys, read-after-write reconciliation, and honest pending states are the practical contract. Always-on proactive delivery requires an always-on runtime; a local computer asleep on Saturday morning cannot send on time.

The sequencing deliberately repairs the existing memory loop and delivery path before adding many new capabilities. Calendar, departure guidance, and purchase then validate a reusable task engine instead of becoming isolated feature branches.
